# درس ۱ — پایه‌ی پروژه (فاز ۱ و ۲)

> این فایل برای یادگیری خودت است، نه برای recruiter.

## از کجا شروع کنی

تاریخچه‌ی Git را به ترتیب بخوان. هر commit یک قدم است:

```bash
git log --oneline --reverse
git show <hash> --stat     # کدام فایل‌ها تغییر کردند
git show <hash>            # دقیقاً چه خطوطی
```

| Commit                     | چه کرد                      | چرا جدا commit شد                             |
| -------------------------- | --------------------------- | --------------------------------------------- |
| `chore: scaffold`          | خروجی خام `create-next-app` | تا ببینی **من** چه چیزی را عوض کردم، نه ابزار |
| `docs: requirements + ADR` | تصمیم‌ها قبل از کد          | اول «چرا»، بعد «چطور»                         |
| `build: harden toolchain`  | تنظیمات سخت‌گیرانه          | هسته‌ی این درس                                |
| `ci: GitHub Actions`       | بررسی خودکار در هر push     | کد بد به `main` نرسد                          |

مهم‌ترین تمرین: `git show` روی commit سوم و خط‌به‌خط خواندنش.

## ۵ مفهوم کلیدی

### ۱. Server Component

در App Router هر کامپوننت **به‌صورت پیش‌فرض روی سرور اجرا می‌شود**. خروجی‌اش HTML است و هیچ JavaScript ای برای آن به مرورگر نمی‌رود.
فقط وقتی `"use client"` بالای فایل بنویسی، کامپوننت به مرورگر فرستاده می‌شود. ما این کار را فقط برای چیزهای تعاملی می‌کنیم: منوی موبایل و فرم.

**بیلد را ببین:** کنار `/` علامت `○ (Static)` آمده. یعنی صفحه یک بار موقع build ساخته می‌شود و بعد فقط HTML آماده تحویل داده می‌شود. این سریع‌ترین حالت ممکن است.

### ۲. TypeScript سخت‌گیر — `noUncheckedIndexedAccess`

```ts
const projects = ["a", "b"];
const first = projects[0]; // بدون این گزینه: string  ← دروغ!
// با این گزینه:  string | undefined ← حقیقت
first.toUpperCase(); // ❌ خطا: شاید undefined باشد
```

آرایه‌ی خالی در production اتفاق می‌افتد. این گزینه مجبورت می‌کند این حالت را در نظر بگیری.

### ۳. هدرهای امنیتی (`next.config.ts`)

هر پاسخ سرور چند دستور امنیتی به مرورگر می‌دهد. توضیح هر کدام کنار خودش در فایل نوشته شده.
خودم روی سرور محلی تست کردم و خروجی واقعی این بود:

```
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Strict-Transport-Security: max-age=63072000; includeSubDomains
```

⚠️ **CSP عمداً هنوز اضافه نشده.** CSP قوی‌ترین هدر است، اما با Next.js به nonce نیاز دارد. اگر سرسری اضافه شود، سایت را می‌شکند. این کار در فاز امنیت انجام می‌شود. نوشتن این محدودیت در README یعنی صداقت مهندسی.

### ۴. `output: "standalone"`

`pnpm build` یک پوشه‌ی `.next/standalone` می‌سازد که فقط فایل‌های لازم برای اجرا را دارد.
نتیجه: Docker image کوچک می‌شود و `node server.js` بدون `pnpm install` روی سرور اجرا می‌شود. این برای deploy روی TySia است.

### ۵. یک خطای واقعی: فونت Google

اولین build **شکست خورد**:

```
Failed to fetch Geist from Google Fonts.
```

دلیلش این بود که `next/font/google` موقع build به اینترنت وصل می‌شود. اگر Google در دسترس نباشد، یا CI یا سرور محدودیت شبکه داشته باشد، deploy متوقف می‌شود.
راه‌حل این بود که فونت را از پکیج npm به اسم `geist` بگیریم، که فایل‌هایش داخل خود پروژه است.
درس مهندسی: **build باید hermetic باشد**، یعنی فقط به چیزهایی وابسته باشد که در lockfile ثبت شده‌اند.

## تمرین‌ها (اجباری)

**تمرین ۱ — پیش‌بینی (بدون اجرا جواب بده):**
اگر در `page.tsx` بنویسی `const x: any = 5;` کدام بررسی شکست می‌خورد؟ lint، typecheck، یا هیچ‌کدام؟ چرا؟

**تمرین ۲ — دست به کد:**
عنوان صفحه (همان چیزی که در تب مرورگر می‌بینی) را عوض کن. باید بفهمی کدام فایل را باید تغییر بدهی.
بعد `pnpm check` را اجرا کن و commit بزن، با پیامی به سبک commitهای قبلی.

**تمرین ۳ — امنیت:**
با `curl -I` هدرها را روی سرور محلی ببین. توضیح بده اگر `X-Frame-Options` نبود، یک مهاجم چطور می‌توانست از آن سوءاستفاده کند. (کلیدواژه: clickjacking)

جواب‌ها را برایم بفرست تا review کنم.
